# Debian agent zones: deployment plan

Debian is the standard for all development machines and agent virtual machines (VMs). Production servers and the development containers used for their [Computor application](https://github.com/computor-org/computor-infra) are explicit exceptions to this standard.

Use two persistent Debian 13 VMs for the agent zones, with security policy enforced outside each guest. The decision is accepted; deployment and boundary validation are pending. The new tooling is being developed in [the infrastructure repository](https://github.com/itpplasma/code). Existing Incus and Multipass profiles remain separate legacy environments and do not satisfy this plan.

| Zone | Permitted data and services |
|---|---|
| Confidential | Authorized confidential and internal data; Pi and local models; scoped mail and Nextcloud operations. No cloud-model or general Internet route. Sending, forwarding, sharing and export require separate human authorization. |
| Internal | Files explicitly approved for the configured cloud providers and usual mail permitted by the rule below; Claude, Codex, Pi and approved local models. No direct TU network or system access; scoped mail is the current exception. |

For now, the internal zone may read usual mail only when it is already marked read and is outside the `confidential` folder. The mail owner service enforces this against current mailbox state for search, message retrieval, threads, previews and attachments, including their metadata and counters. A thread response may contain only eligible messages. No per-message approval is required for these ordinary reads. Agents cannot gain access by marking unread mail read or moving mail out of `confidential`; the internal endpoint must deny those changes. The confidential zone retains full authorized mail access.

Files without a known classification default to confidential. The internal Nextcloud view remains an approved local replica, without guest-triggered TU requests or automatic writeback. A model may suggest classification but cannot authorize changing file access or releasing confidential content.

Human approval for changing file classification, expanding file access or exporting confidential files is recorded outside the guests and agent-controlled sessions, enforced by the owning service, and bound to the exact content version, destination and operation.

Apple Silicon Macs use native ARM64 Debian guests with [vfkit and Apple's Virtualization.framework](https://github.com/crc-org/vfkit/blob/main/doc/usage.md). Linux institute PCs use Debian amd64 guests with QEMU and Linux Kernel-based Virtual Machine (KVM) acceleration. Guest setup, policy and commands are shared; host transport and service adapters differ. Start each VM with four virtual CPUs, 4 GiB RAM and a 64 GiB sparse disk. Measure before increasing resources. Stopping an unused VM returns its memory; balloon reclamation remains an acceptance test.

The planned entry points are `ai internal`, `ai confidential` and `ai internal -- COMMAND`, with automatic startup and concurrent shells in the persistent guest. SSH uses a private virtual-socket channel, pinned guest host keys and no agent, X11 or port forwarding. Production guests have no external network interface, host-directory share, clipboard, USB, personal Keychain or host management interface. Assume guest root is compromised.

Mac channels map fixed guest ports to predetermined Unix sockets. Linux must use a separate [vhost-device-vsock Unix-socket backend](https://github.com/rust-vmm/vhost-device/blob/main/vhost-device-vsock/README.md) for each VM, with separate accounts and groups and no `--forward-cid`. Ordinary kernel vsock is not the selected boundary. Test that arbitrary ports, host listeners and the sibling VM remain unreachable.

Deploy in the following order. A stage passes only when its behavior is demonstrated; configuration files alone are insufficient evidence.

1. **Build the reproducible guest.** Pin an immutable official [Debian cloud-image build](https://cloud.debian.org/images/cloud/trixie/), its architecture and checksum. Prepare packages and agent tools in a disposable build VM with temporary networking, no production credentials and no host mounts. Record the Debian package snapshot and versions, exact tool commits and artifact hashes. Generate separate operator and per-instance guest SSH identities, bake bounded socket relays and create an immutable base. Remove the build NIC and seed before production. Production first boot must not depend on downloading packages.

2. **Install the protected host foundation.** Create distinct nonadministrator identities for each hypervisor, broker and scoped integration service. Install reviewed code, interpreters, dependencies, service definitions, policy, working directories and search paths under root-controlled ownership. Neither guests nor service accounts may change this execution chain. Keep zone disks, sockets, credentials, files and client state separate; cap logs and storage. Verify ownership and reject symlinks and writable ancestors. Retain the existing oMLX inference server using native Metal behind the Slopgate model gateway: one 125-billion-parameter model per Mac host, serving mixed concurrent requests from both zones. Both zones trust that shared inference service; separate model processes, duplicate models and model switching are not required. Guests receive only fixed inference routes, without access to model administration or other clients' requests, logs and cache files. Enforce fixed peers and destinations below broker processes, including attempts through DNS and other host services. This operating-system confinement remains a production gate.

3. **Add scoped services.** Model Context Protocol (MCP) integrations, including [Sloptools](https://github.com/sloppy-org/sloptools) and [Helpy](https://github.com/sloppy-org/helpy), need restricted endpoints at their owning services. Do not forward a generic namespace through a filter. Validate complete typed schemas, reject unknown nested fields, and authorize each operation, account and object. Guests cannot select configuration paths, credentials, commands, upstreams or plugins. Internal services hold no confidential credentials. Untrusted documents and previews run without network or secrets. Missing policy and service failures must deny access.

4. **Complete model compatibility.** Confidential services permit fixed local models only, without cloud fallback, telemetry or URL retrieval. Internal cloud gateways allow the required provider paths and fields, deny tunnels and remote connectors, and hold narrowly scoped credentials outside guests. Test actual Claude, Codex and Pi authentication, refresh, streaming and normal workloads. A basic local chat endpoint does not establish compatibility with these clients. Scoped mail/Nextcloud owner endpoints and provider gateways remain required integrations.

5. **Validate both platforms with synthetic data.** Boot both zones without a NIC; test concurrent SSH sessions, persistence, restart, shutdown and fresh-host rebuild. As guest root, attempt host mounts, arbitrary sockets, direct Internet/TU access, sibling access, cross-zone identifiers and metadata, traversal, symlinks, configuration overrides, arbitrary commands and unauthorized releases. Verify mail access changes with current read/folder state, stale results cannot bypass checks, mixed threads omit ineligible messages, and agents cannot change flags or folders to gain access. Repeat relevant attacks under each host service identity. Observe host traffic and backend audit records. Test expired credentials, missing policy, crashes, resource exhaustion, update and rollback. Linux transport isolation requires its own runtime results.

6. **Test encrypted recovery.** Keep VM disks and service state on FileVault-protected Mac storage, and use encrypted Linux storage such as LUKS plus encrypted backups. Before enabling FileVault, stage Apple's Remote Login and recovery access while retaining the existing SSH path. Apple supports [remote FileVault unlock on Apple Silicon with macOS 26 or later](https://support.apple.com/guide/security/managing-filevault-sec8447f5049/web), provided Remote Login and a network connection are available. Prove cold-boot reachability without depending on a VPN that starts after login. Test headless service credentials separately; do not rely on automatic login-Keychain availability. Replace the old SSH service only after recovery succeeds.

7. **Migrate and cut over.** Inventory and classify real files, provision dedicated credentials, then migrate only through boundaries that passed. Enable mail under the current-state rule above. Confirm normal agent, shell, mail, data and model workflows. Revoke broad host-agent credentials and stop agentic AI on the outer host after the replacement works.

For subsequent updates, agents submit infrastructure pull requests with exact upstream `main` commits, hashes, build recipes, configuration differences, migration steps and rollback compatibility. Disposable unprivileged builds produce an immutable bundle. A human approves and signs that exact bundle; the signing key is unavailable to agents. A root-owned deterministic installer verifies the signature and hashes, installs bounded files atomically and runs no release hooks as root. Agents and service accounts cannot invoke it. Policy expansion requires separate approval. Rollback retains current policy, secrets and revocations; incompatible older code fails closed.

This design limits the authority of a compromised guest. Shared hardware and vulnerabilities in the hypervisor, host or authorized services remain residual risks. Real data stays out until the corresponding acceptance gates pass.
